# HotShop 实施任务目录

任务必须满足依赖关系后才能开始。一个实现对话原则上只承担一个任务；任务未通过全局验收，不开始依赖它
的后续任务。编号表达总体演进顺序，不表示所有任务都必须串行；只有
`PARALLEL_EXECUTION.md` 中由全局验收对话明确发放的波次可以并行。

## 路线总览

| 阶段 | 任务 | 主要交付 |
|---|---|---|
| 基线 | TASK-00～03 | 现状基线、工具链、数据库迁移、容器环境 |
| 平台 | TASK-04～06 | API 规范、鉴权、审计 |
| 交易 | TASK-07～10 | 秒杀预约、异步订单、可靠消息、模拟支付 |
| 可观测 | TASK-11 | 指标、日志、追踪和仪表盘 |
| 前端 | TASK-12～14 | React 基座、用户端、管理端 |
| Agent | TASK-15～17 | Agent 基座、工具授权、RAG 与评测 |
| 验证 | TASK-18～21 | CI、E2E/安全、压测、文档与简历 |

## TASK-00：现状基线与特征测试

### 目标

在升级技术栈前建立可重复的现状基线，区分原有缺陷和改造引入的回归。

### 工作范围

- 盘点模块依赖、启动入口、配置加载、端口、数据库表、Redis Key、RabbitMQ 拓扑和已有接口。
- 输出当前架构图和已知问题清单，特别标出：
  - RabbitMQ 超时时间计算；
  - publisher confirm 处理；
  - 简单 Redis 锁的 TTL/释放安全；
  - 定时扫描订单；
  - 数据库条件扣库存；
  - 编码乱码。
- 为当前能够稳定描述的核心行为补充最小特征测试，不改变业务语义。
- 建立统一的本地验证命令文档。

### 禁止事项

- 不升级 Java/Spring Boot。
- 不重写交易流程。
- 不修复盘点出的业务缺陷；缺陷只记录，留给对应任务。

### 验收标准

- `docs/architecture/current-state.md` 能让陌生开发者定位各入口与依赖。
- `docs/quality/baseline.md` 列出实际执行的命令、成功项和失败项。
- 已知问题包含代码位置、触发条件和后续任务编号。
- 新增特征测试可重复执行，且未通过的旧行为不得伪装为通过。

## TASK-01：Java 21 与构建基线

### 目标

将项目升级到统一、可复现的现代 Java 构建基线。

### 工作范围

- 升级 Java 21 和当前稳定的 Spring Boot 3.5.x，统一 Spring 依赖版本管理。
- 校验 MyBatis Starter 3.0.x 与其他依赖兼容性，删除无必要的显式 Spring 版本。
- 补全并验证 Maven Wrapper，固定插件版本和 UTF-8 编码。
- 配置编译、单元测试、集成测试分层执行，以及合理的构建失败策略。
- 修复升级造成的编译或测试问题，但不改变交易架构。
- 增加 `.gitattributes`，防止源码和文档跨平台乱码。

### 验收标准

- Windows 和 Linux 容器均可使用 `./mvnw` 或 `mvnw.cmd` 构建。
- `java.version` 为 21，Spring Boot 统一为选定的 3.5.x。
- 所有模块完成 clean verify；如旧测试需要外部环境，应被明确分到集成测试而非直接跳过。
- README 中不再要求开发者自行安装不一致的 Maven 版本。

## TASK-02：Flyway 与数据库约束

### 目标

用可追踪的迁移替代一次性初始化脚本，建立无外键的数据一致性基础。

### 工作范围

- 从现有 `init.sql` 梳理基线迁移，建立 Flyway 目录和版本规则。
- 设计用户、商品、活动、订单、订单项、预约、支付单、刷新令牌、Outbox、Inbox、审计日志等表的演进路径。
- 添加必要的主键、唯一键、非空、检查约束和索引。
- 明确所有状态枚举、金额精度、时间精度、逻辑删除及乐观并发字段。
- 准备可重复生成的开发数据和独立的压测数据生成方案。
- 编写约束测试，证明重复业务键、非法状态值和负数金额会被拒绝。

### 禁止事项

- 任何数据库外键或级联规则。
- 将 Flyway 与容器 `init.sql` 同时作为结构事实来源。
- 在应用启动时静默修改生产结构。

### 验收标准

- 空数据库能迁移到最新版本；已有基线库有明确的接管说明。
- `flyway_schema_history` 校验通过，重复启动不重复建表。
- 仓库扫描不存在 `FOREIGN KEY`。
- 索引说明包含查询场景与列顺序，而非只罗列名称。

## TASK-03：Docker Compose 数据基础设施

### 目标

提供适合开发、测试和后续压测的本机容器环境。

### 工作范围

- 在保护现有 Compose 改动的前提下，拆分 `redis-cache` 与 `redis-seckill`。
- 为 seckill Redis 配置 `noeviction`、AOF + RDB 和持久卷；cache Redis 使用可解释的淘汰策略。
- RabbitMQ 改为官方能力可复现的镜像，不安装 delayed-message 插件；配置管理端、健康检查和持久卷。
- MySQL 配置健康检查、字符集、时区、资源限制和可观测参数。
- 提供基础、应用、可观测、测试等 Compose profile 或等价的清晰启动方式。
- 使用 `.env.example` 管理非敏感默认项，实际密钥不入库。
- 验证停止、重启后持久化数据和健康状态。

### 验收标准

- 一条文档化命令可启动数据基础设施。
- 两个 Redis 只使用 DB 0，配置和用途不同。
- RabbitMQ 不含延迟消息插件。
- `docker compose config` 通过，所有关键服务有健康检查。
- 现有 Docker 用户改动被吸收而非覆盖。

## TASK-04：API 契约与错误规范

### 目标

先稳定前后端和 Agent 都要依赖的接口协议。

### 工作范围

- 定义 `/api/v1`、`/admin/api/v1`、`/agent/api/v1` 的边界。
- 引入 DTO 映射，禁止 Controller 返回持久化实体。
- 使用 RFC 9457 Problem Details 或 Spring 对应实现统一错误响应。
- 定义请求 ID、Trace ID、时间格式、金额格式、稳定游标分页和幂等键语义。
- 按用户、管理员、Agent 分组生成 OpenAPI。
- 建立 OpenAPI 生成 TypeScript 客户端的脚本和破坏性变更检查。
- 为典型成功、校验失败、未认证、无权限、冲突、限流响应编写契约测试。

### 验收标准

- OpenAPI 能在干净环境生成，不需要手工修改生成文件。
- 错误响应不泄露堆栈、SQL 或内部类名。
- 分页在相同排序值和并发插入时仍稳定。
- 契约测试覆盖至少一个匿名接口、用户接口和管理接口。

## TASK-05：分域鉴权与令牌轮换

### 目标

建立用户、管理员和 Agent 委托不可混用的身份体系。

### 工作范围

- 使用非对称密钥签发短时 Access JWT，验证 issuer、audience、过期时间和签名算法。
- 门户用户、管理员、Agent delegation 使用独立 issuer/audience 或等价的严格验证链。
- Refresh Token 使用高熵随机值，通过 HttpOnly/Secure/SameSite Cookie 传递，服务端只存哈希。
- 实现 refresh rotation、token family、复用检测、注销和全家族撤销。
- 定义角色、权限、资源归属和方法级授权。
- 对登录、刷新、失败登录、敏感接口配置分层限流。
- 为跨 audience、降权绕过、他人订单、过期、撤销、重复刷新和并发刷新编写测试。

### 禁止事项

- 在 localStorage 保存 Refresh Token。
- 仅依靠前端隐藏菜单实现权限。
- 共享硬编码 HMAC 密钥。

### 验收标准

- 用户 Token 无法调用管理接口，管理员 Token 不能作为 Agent 委托 Token。
- 旧 Refresh Token 在轮换后再次使用会撤销对应家族并留下审计事件。
- 身份测试使用 Testcontainers 或等价真实依赖验证，而非全部 Mock。

## TASK-06：统一审计日志

### 目标

让管理、交易异常与 Agent 行为可追责、可关联、不可由业务接口篡改。

### 工作范围

- 设计只追加审计表和统一写入接口。
- 记录 actor 类型与 ID、delegated actor、动作、资源、结果、请求 ID、Trace ID、来源和脱敏摘要。
- 接入管理员写操作、登录安全事件、令牌家族撤销。
- 建立脱敏策略和测试，禁止保存密码、Token、API Key、Cookie、完整提示词或思维链。
- 提供仅管理员可读的查询 API，支持时间、actor、动作、资源和结果过滤。

### 验收标准

- 普通业务 API 不存在更新或删除审计记录的能力。
- 写业务失败时审计策略有清晰定义并被测试。
- 敏感值扫描测试通过。
- 越权查询审计日志被拒绝。

## TASK-07：Redis Lua 秒杀接入

### 目标

实现低延迟、原子、可验证的秒杀预约入口。

### 工作范围

- 定义活动装载、库存、用户预约、幂等键和 Stream 的 Key 规范与 hash tag 策略。
- 单个 Lua 脚本原子完成：活动状态检查、限购检查、库存预扣、预约记录、`XADD`。
- HTTP 接口快速返回 reservation/request ID，不同步写 MySQL 订单。
- 定义重复请求、库存不足、活动未开始/已结束和 Redis 不可用的响应。
- 实现活动数据从 MySQL 到 Redis 的可重复装载和校验。
- 以并发测试证明库存不为负、同一用户只有一份有效预约、重复幂等键结果一致。

### 验收标准

- Lua 脚本及返回码有文档和自动化测试。
- 请求路径上没有数据库写入、远程模型调用或全局锁。
- Redis `noeviction`/内存不足场景有明确失败语义，不能静默丢事件。
- 测试后 Redis 预约数、Stream 事件数和剩余库存能够对账。

## TASK-08：Stream 异步订单与补偿

### 目标

可靠地把 Redis 预约转换为 MySQL 订单，并处理崩溃、重复和永久失败。

### 工作范围

- 建立消费者组，使用手动 ACK。
- MySQL 事务内创建订单、订单项、预约落库和必要的 Outbox 事件。
- 使用业务唯一约束和条件 SQL 处理重复消费，不依赖简单分布式锁。
- 处理 Pending List：空闲消息认领、有限重试、毒消息隔离和告警指标。
- 实现 `RESERVED → ORDER_CREATED` 与补偿状态机。
- 补偿 Lua 只允许合法状态归还一次库存并解除用户占位。
- 增加定时对账：Redis 预约、Stream、MySQL 订单和补偿记录不一致时可发现、可修复或进入人工队列。
- 使用容器重启或故障注入验证 ACK 前后崩溃。

### 验收标准

- 重复消息不能生成第二个有效订单或重复扣库存。
- 消费者在事务提交前、提交后但 ACK 前崩溃均能恢复。
- 永久失败最终补偿一次，并留下审计和指标。
- 对账任务有 dry-run 模式，不会盲目修改数据。

## TASK-09：Outbox/Inbox 与 RabbitMQ

### 目标

让数据库状态变化与业务事件最终一致，避免消息静默丢失。

### 工作范围

- 业务事务内写 Outbox；异步发布器按批次锁定、发布、confirm、重试。
- 启用 publisher confirm 和 mandatory，处理 nack、return、超时和进程重启。
- 使用有限指数退避、最大次数、失败状态和运维重放接口。
- RabbitMQ 消费者手动 ACK；使用 Inbox `(consumer_name,event_id)` 或业务唯一约束保证幂等效果。
- 为固定订单超时建立 TTL 队列 + DLX，不使用 delayed-message 插件。
- 修复现有超时分钟换算错误并加入边界测试。
- 清除只打印 confirm、无限重试和不安全 ACK 等旧路径。

### 验收标准

- 事务回滚时没有可发布事件，事务提交后的事件最终可发布。
- 重复投递、消费者重启和 RabbitMQ 短暂不可用不产生重复业务效果。
- 不可路由消息可见、可告警、可重放。
- 仓库及镜像不依赖 delayed-message 插件。

## TASK-10：Mock Payment 与订单终态竞争

### 目标

模拟真实支付回调中的签名、防重放、重复通知和状态竞争。

### 工作范围

- 定义 Payment Provider 接口和 Mock 实现，明确标注非真实支付。
- 创建支付单和模拟收银台，支持成功、失败、延迟、重复回调。
- 回调校验签名、时间戳、nonce、订单金额和商户订单号。
- 使用唯一回调 ID 与 Inbox/条件更新实现幂等。
- 支付成功与超时关单竞争时，只允许一个合法终态；迟到回调进入明确的异常处理路径。
- 发布支付结果和关单结果事件，库存释放必须唯一。
- 编写并发竞态、重复回调、篡改金额、过期签名和重放测试。

### 验收标准

- 同一订单不可能同时为 PAID 和 CANCELLED。
- 任意数量重复通知只产生一次支付业务效果。
- 伪造或过期回调返回安全错误并写审计。
- Playwright 可在后续任务调用稳定的模拟支付流程。

- 重启可观测容器后配置仍可复现。

## TASK-15：Agent 服务基座与流式会话

### 目标

建立可替换模型、可测试、不会影响交易核心可用性的 Agent 服务。

### 工作范围

- FastAPI + LangGraph 工程、依赖锁定、配置分层、健康检查和 Dockerfile。
- 定义 Model Provider；实现 FakeModel 和百炼 Qwen 适配器，真实 Key 仅从环境读取。
- 建立会话、消息、结构化 SSE 事件和取消机制。
- 用户端与管理端使用不同入口、audience 校验、工具注册表和系统策略。
- 超时、重试、熔断、并发限制和 token/费用指标。
- Agent 不可用时交易与普通查询仍正常工作。

### 验收标准

- 无 API Key 时 FakeModel 模式可完整运行和测试。
- CI 不调用任何付费模型。
- SSE 不输出内部思维链或敏感配置。
- 用户 Token、管理员 Token、Agent delegation Token 不能互换。

## TASK-16：Agent 工具、确认令牌与权限

### 目标

实现最小权限的实时工具调用和可证明安全的写操作确认。

### 工作范围

- 用户工具：商品查询/比较、本人订单查询、购买草稿。
- 管理工具：只读统计、异常摘要、低风险配置草稿。
- 工具参数使用严格 Schema；每次调用重新校验身份、资源归属和 scope。
- 购买草稿不扣库存、不创建订单；用户确认后签发绑定用户、动作、参数摘要、过期时间和 nonce 的一次性令牌。
- Java 交易 API 原子消费确认令牌；重放、篡改参数、跨用户使用均失败。
- 工具调用写审计并携带 Trace ID。
- 建立完整越权测试矩阵。

### 禁止事项

- Agent 直接访问数据库。
- Agent 执行任意 SQL、任意 URL、Shell 或动态工具名。
- 向管理 Agent 开放退款、补偿、消息重放、权限修改、用户封禁等高风险动作。

### 验收标准

- 未授权 Agent 测试 100% 阻断。
- 模型即使输出伪造工具参数，也无法越权或绕过确认。
- 同一确认令牌只能成功消费一次。

## TASK-20：k6 压测与性能调优

### 目标

在固定本机环境形成可复现、可解释、不会伪造的性能结论。

### 工作范围

- 建立 smoke、baseline、load、stress、spike、soak 六类 k6 场景。
- 区分匿名浏览、登录、秒杀接入和异步完成指标，不把异步接口响应当作订单完成。
- 准备固定规模数据集、用户池、库存和幂等键；记录预热和清理方式。
- 先建立基线，再基于指标定位瓶颈并逐项调优；保留调优前后证据。
- 比较平台线程与虚拟线程，只有实测收益且无依赖问题才启用。
- 压测容器设置资源限制，记录本机硬件、Docker 资源、版本、时间和误差。
- 测后以 MySQL 和 Redis 对账证明零超卖、零重复有效订单、零账实差异。

### 验收标准

- 10,000 VUs、5,000 req/s、P99 目标只按实测结果判定，未达标如实报告。
- 压测脚本、数据生成、启动命令、dashboard 和结果摘要均入库。
- 报告区分接入延迟和端到端订单完成延迟。
- 不以单次峰值、被限流请求或错误请求冒充有效吞吐。
