## 结果口径

只将窗口内成功完成数除以 60 秒作为该窗口的完成速率；窗口后的 graceful-stop 请求单列。
`actualRps` 兼容字段包含收尾请求，不能据此宣称稳态吞吐。P95/P99 为对应 HTTP 请求耗时，预约异步建单延迟另按持久化时间戳统计。

| 2 CPU / 登录 | 803 | 32 | 13.383 | 366 | 2757.466 / 3009.835 |
| 2 CPU / 普通购买 | 1200 | 0 | 20.000 | 0 | 23.739 / 36.788 |
| 2 CPU / 预约 | 1200 | 0 | 20.000 | 0 | 8.427 / 9.883 |
| 4 CPU / 登录 | 1198 | 3 | 19.967 | 0 | 165.530 / 592.338 |
| 4 CPU / 普通购买 | 1200 | 1 | 20.000 | 0 | 23.554 / 45.730 |
| 4 CPU / 预约 | 1200 | 1 | 20.000 | 0 | 8.733 / 11.031 |

2 CPU 登录阶段 Portal 采样峰值为 203.78% CPU，k6 约 9.77%；4 CPU 对照改善了完成量与尾延迟，支持“此负载下 Portal CPU 配额限制登录吞吐”的判断。一次对照尚不代表长期容量或所有硬件上的收益。

2 CPU 普通购买创建 1200 个订单，库存从 1201 降到 1，无重复用户订单，创建与超时消息均有发布事实。预约同样完成 1200 笔，MySQL/Redis 库存一致，无超卖、重复订单、遗留处理消息或对账差异；异步建单 P95 为 705.398 ms、P99 为 1679.747 ms。合法延时队列和无消费者的集成队列由逐订单发布事实解释，不伪称 RabbitMQ 全队列为空。

4 CPU 普通购买和预约分别完成 1201 笔，其中各 1 笔在窗口后完成，库存均从 1201 降到 0；相同正确性检查通过。预约异步建单 P95 为 1039.996 ms、P99 为 1991.317 ms，没有随登录改善而同步降低。两组 `businessCorrectnessPassed`、`runIntegrityPassed` 和 `ownedResourcesZero` 均为 true，5000 RPS 达成标记均为 false。

## 中断与恢复

| 场景 | 发现与修复 | 验证方式 |
| --- | --- | --- |
| 两标签同时恢复登录 | 原先竞争同一 refresh cookie，实测返回 `[200,401]` 并撤销 family；现按同源身份域取得 Web Lock 后读取 CSRF，返回 `[200,200]`，再刷新仍正常 | 两个真实页面共享 cookie，延迟请求扩大竞争窗口；另有等待期间退出的单元回归 |
| Refresh 已轮换但响应丢失 | 不自动重试未知结果；显示“需要重新登录”，登录后回到原页面 | 实际服务端处理成功后丢弃响应，检查只有一次轮换，再从页面登录 |
| 普通购买响应丢失 | 刷新后保留原幂等键，重试恢复同一订单，时间线仅一个创建事件 | 实际创建成功后断开响应，再刷新并购买 |
| 订单流断网重连 | 原实现追平事件后等待约 16 秒才发心跳；现在空流首次轮询即发心跳，保持原游标 | 浏览器离线/上线，检查恢复实时状态及事件不重复；Java 回归检查追平游标后的首心跳 |
| Agent SSE 被截断 | 保留问题、清除不完整购买草稿，等待用户手动重发 | 截掉真实事件流的完成事件，再验证重发 |
| Agent 进程重启 | 旧会话 404 后丢弃旧句柄并保留问题；重发创建新会话，购买仍需确认 | 创建 run 后真实重启专用 Agent 容器，再订阅和恢复 |

恢复脚本需要已有本机演示、Web 依赖及 Playwright Chromium：

```powershell
pwsh -NoProfile -File .\script\verify-browser-recovery.ps1 `
  -DemoProject hotshop-task21-shop1002 -DemoUrl http://127.0.0.1:18083
```

将项目名与地址替换为自己的演示。脚本在所选演示中创建测试账号和订单，另建带所有权标签的临时 Agent、独立 Redis 与本机 Vite；只重启临时 Agent。默认使用 18085/18086 端口，可通过参数修改。结束后移除临时进程、容器和凭据文件，证据保存在 `.local/verification/<RunId>/`。浏览器记录不保存 trace、截图或视频，避免认证内容进入附件。

## 验证边界与失败记录

- Java 订单 SSE 定向测试 10 项通过；固定锁文件的容器内 Web 单元测试 118 项通过，格式、类型与 lint 检查通过。Portal 与 Nginx 生产镜像构建通过，已更新本机演示。
- 固定依赖的桌面/手机回归 30 项通过（1.1 分钟），覆盖认证隔离、账号切换、商品筛选、失败重试、键盘导航、减少动效、对比度与 320–1440px 布局。负载规划、正确性策略及 Compose/k6 静态检查通过。
- 真实恢复整组 5 项通过（`recovery-1003e`，40.9 秒），临时进程、Agent、Redis 与凭据文件清理成功。早一轮中订单重连停留“正在重连”的失败由首心跳修复消除。
- 第一次负载 smoke 受多个本机验收栈争用资源影响，出现 Docker EOF；停下本任务的旧验收栈后，新 Run ID 的 smoke 三阶段通过，失败目录保留。
- 第一次恢复夹具未登录，产生 403；修正后才取得真实的多标签 `[200,401]` 红测。助手隔离容器最初使用不支持的 Redis 命名空间而启动失败，之后改为独立 Redis，未放宽应用校验。
- 本机旧依赖目录和 Windows 换行影响过格式检查；固定依赖的容器格式检查通过。第一次桌面/手机容器限制为 1 GiB/2 CPU，触及内存限制并出现页面加载超时；停止该次运行，改为 2 GiB/4 CPU、一个浏览器 worker 单独复验。
- Web Locks 只覆盖支持该 API 的同源安全上下文。Agent 重启恢复为手动新会话，不宣称跨进程事件重放。此处使用 FakeModel，不评价真实模型质量或延迟。
